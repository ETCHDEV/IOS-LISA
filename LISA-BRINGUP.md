## Approach inherited from Sweet

An unlocked Xiaomi bootloader temporarily boots an Android boot image containing a freestanding ARM64 shim. The shim reads the live FDT, loads an XNU Mach-O and generated Apple device tree, and passes boot arguments. The patched XNU implements Qualcomm platform support and an HFS+ root in userdata; iOS userland is prepared separately from an Apple IPSW. Sweet's working hardware observations and build procedures are in `ios-sweet/NOTES.md` and `ios-sweet/README.md`.

## Lisa-specific obstacles

- The Lisa mainline DTS describes a 1080x2400, 4320-byte-stride a8r8g8b8 framebuffer at `0xe1000000`. Sweet hardcodes `0x9c000000` in the shim, ADT generator, and early XNU debug patch 0010. The mainline framebuffer address must be checked against the actual bootloader and stock FDT before accessing it.
- Sweet's default lower-memory ADT begins at `0xb0000000`; Lisa's DTS reserves `0xc0000000–0xc5100000`, `0xd0800000–0xd7ef7000`, and other regions above it. The default range overlaps those reservations. Even the alternative upper bank must be established from the actual memory map and protected regions before use; memory size and XPU restrictions cannot be inferred from the panel DTS alone.
- Lisa describes Goodix GT9897 on SPI13, with GPIO 81 interrupt, GPIO 105 reset, and L7C/L2C supplies. Sweet's GT9896 driver uses GENI I²C SE7 and a different power vote. The existing touch driver cannot simply be reused.
- Lisa uses different PMICs (PM7325, PM7325B, PM7350C, PMK7325). Sweet's key and regulator register assumptions need verification against Lisa's actual firmware and SoC definitions.
- Lisa enables UFS and USB in its DTS, but that does not establish register compatibility, firmware state, clocks, access permissions, or DMA safety with the Sweet drivers. Sweet's persistent logger writes the end of userdata by default; its root workflow overwrites userdata. Disable all storage writes and probing that changes hardware state during initial diagnostics. `sweetlog=0` only disables the logger; it does not make the rest of the Sweet image safe for Lisa.
- The stock boot image header, DTB/DTBO, firmware state, RAM map, CPU features, GIC/timer/PSCI configuration and bootloader handoff must be measured on the target. A mainline DTS is not a drop-in stock DTB.

## Next milestone: non-destructive hardware discovery

1. Obtain the exact Lisa variant, installed firmware and bootloader status, and stock `boot.img`, `dtbo.img`, `vbmeta.img` and live device tree from the target. Keep device-specific dumps and identifiers outside git. Back up calibration and boot partitions before experimentation.
2. Compare the live tree and stock boot header with upstream's shim assumptions. Establish an actually safe framebuffer and RAM window, including all reserved regions and access protections. Confirm the CPU's 16 KiB translation support, exception level, PSCI conduit and interrupt configuration on hardware.
3. Build a Lisa-specific diagnostic shim using the stock boot format and DTB, with framebuffer and RAM addresses derived from verified facts. Start without an XNU payload or storage writes. A temporary `fastboot boot` still executes privileged code and can hang or corrupt hardware state; verify behavior and recovery on the actual device.
4. Only after those checks, adapt XNU's early framebuffer, memory/ADT, interrupt and CPU initialization, then validate a single-core kernel boot. Add UFS read-only discovery and a safe root strategy before enabling writes; port SPI touch and PMIC keys separately.

No successful build, boot, or functional iOS port is claimed by this assessment. Full bring-up requires target access, appropriate build infrastructure, and iterative device logs. Sweet itself disables major security protections and lacks many phone functions; its iOS userland and firmware are not included in this checkout.
